# Data dictionary: ce_ecosystem.db

Generated by `scripts/cleaning/build_final_database.py`. Do not edit by hand;
edit the script and re-run:

    python -m scripts.cleaning.build_final_database

Outputs land in `data/final/`, which is gitignored along with the rest of
`data/`. The database is 80 MB and is deliberately not committed: the script
is what is shared, and anyone who needs the database builds it.
`data/final/BUILD_MANIFEST.md` records the exact input files, their sizes and
their SHA-256 hashes for the build that produced the current database.

All elapsed-time fields are measured to a fixed reference date of
**2026-08-06**, the collection date, so they do not drift between runs.

Two files are produced from the same tables:

- **`ce_ecosystem.db`** — SQLite, the working source for all analysis.
- **`ce_ecosystem.xlsx`** — the same tables for browsing, with long text
  columns (abstracts, descriptions, author id lists) dropped and the two
  largest link tables omitted. Never analyse from the workbook.

---

## Shape

```
                    project_field_probabilities
                                |
   institutions ── project_institutions ── PROJECTS ── project_outcomes ── OUTCOMES
                                |               |                              |
                                |         source_outcome_links    publication_field_probabilities
                                |                                              |
                                                                    outcome_authors ── authors
```

`project_id` is the key on the input side, `global_outcome_id` on the output
side, and `project_outcomes` is the join between them. That join is the
literal answer to "link the inputs to the outputs".

## `projects` — 1,640 rows, one per project

The input side, with output counts already rolled up so most questions need no
join at all.

### Identity and award
| Column | Meaning |
|---|---|
| `project_id` | GtR project identifier, the primary key throughout |
| `grant_reference` | funder's grant reference |
| `lead_funder` | funding body |
| `grant_category` | award instrument. Strongly predicts output |
| `status` | GtR status |
| `value_gbp` | award value. Missing or zero for 21% of projects, mostly studentships |
| `funding_available` | true where `value_gbp` is present and positive. **Use this as the denominator filter for any funding statistic** |
| `start_date`, `end_date`, `start_year`, `end_year` | award dates |
| `duration_months` | end minus start |
| `months_elapsed` | start to the earlier of end and the reference date. The time actually available to produce output, and the right exposure variable for any productivity comparison |
| `is_complete` | whether the award had ended by the reference date |
| `title_clean`, `abstract_text_clean` | cleaned text |
| `principal_investigator_clean` | PI name where available |
| `gtr_url` | link to the GtR record |

### Lead organisation, from the institution registry
| Column | Meaning |
|---|---|
| `lead_institution_id` | resolved identifier, `ror:...` or `local:...` |
| `lead_institution_name` | canonical name. **Use this, not `lead_organisation`**, which is the raw string and double-counts |
| `lead_org_type` | education, company, nonprofit, government, healthcare, facility, funder, other, unknown |
| `lead_country`, `lead_city`, `lead_lat`, `lead_lon` | from ROR, present where the organisation resolved. 50.4% coverage, because ROR does not cover small UK companies |
| `lead_ror_id` | ROR identifier where matched |
| `lead_organisation` | the original raw string, retained for traceability |
| `n_partner_institutions` | distinct participant organisations |
| `n_partners_<type>` | participants broken down by organisation type |

### Discipline
| Column | Meaning |
|---|---|
| `discipline_field` | assigned discipline, the argmax of the probability distribution |
| `discipline_source` | `funder_assigned` where GtR supplied a subject, `model_assigned` otherwise |
| `discipline_confidence` | the winning probability |
| `discipline_tier` | 1 funder-assigned, 2 model above threshold, 3 model below. **Provisional: see `DATASET_STATUS.md` section 2** |
| `discipline_funder`, `discipline_model`, `discipline_model_confidence` | the funder label and the model label kept separately, so the two can be compared |
| `openalex_field`, `openalex_domain`, `openalex_subfield`, `openalex_topic` | OpenAlex's own topic classification of the project. Kept separate and **not** the same thing as `discipline_field` |

### Output, source-stacked (the convention the Methodology chapter quotes)
| Column | Meaning |
|---|---|
| `n_<outcome_type>` | count for each of the twelve GtR outcome types |
| `n_publications_{gtr,openalex,scopus,wos}` | distinct DOIs per source |
| `n_publications_distinct_doi` | distinct DOIs across all four sources |
| `n_publication_records` | publication records of any kind, DOI or not |
| `has_publication` | at least one publication record. **This is the definition behind the 616 / 1,640 figure** |
| `n_outputs_total` | sum of output-type counts, excluding disseminations, collaborations and further fundings |
| `n_non_publication_outputs` | as above, excluding publications |
| `has_non_publication_output`, `has_any_output` | roll-ups |

### Output, merged and deduplicated
| Column | Meaning |
|---|---|
| `n_merged_<type>` | count per harmonised outcome type from the merged layer |
| `n_outcomes_merged` | distinct outcomes of any type |
| `n_outputs_merged` | distinct outcomes excluding dissemination, collaboration and further funding |
| `n_publications_merged`, `has_publication_merged` | the deduplicated publication count. Gives **615**, against 616 for the stacked definition |
| `n_distinct_doi_merged` | distinct DOIs |
| `has_any_output_merged` | roll-up |

**On what counts as output.** Disseminations (talks, press), collaborations
and further fundings are counted in their own columns but excluded from every
`*_outputs_*` total, because a subsequent grant is an input and a conference
talk is an activity. Including them would flatter the productivity figures. To
change the convention, edit `NOT_OUTPUT` and `MERGED_NOT_OUTPUT` in the
script rather than recomputing by hand.

## `outcomes` — 20,302 rows, one per distinct outcome

The output side. Collapsed from the link-grain `merged/outcomes.csv` by taking
the first non-null value per column across an outcome's link rows.

| Column | Meaning |
|---|---|
| `global_outcome_id` | primary key, assigned by the merge across the four sources |
| `title`, `abstract`, `type`, `subtype`, `year`, `publication_date` | harmonised bibliographic fields |
| `doi`, `doi_norm` | as reported, and lower-cased with the resolver prefix stripped. **Join on `doi_norm`** |
| `source_title`, `url`, `reference_count`, `organisations` | harmonised metadata |
| `cited_by` | citation count as the merge produced it, from OpenAlex or Scopus only. **Null for 4,321 publications, 1,345 of which do have a count in Web of Science.** Kept unchanged so the gap stays visible |
| `cited_by_best` | `cited_by` where present, otherwise `wos_times_cited_all_db`. **Use this for any citation analysis.** Raises publications with a citation count from 5,291 to 6,636 |
| `cited_by_source` | `openalex_or_scopus`, `wos`, or null where neither has one. The recovered WoS counts average 31.8 citations against 32.8 for the rest, so they are not an unusual subset |
| `is_output` | false for dissemination, collaboration and further_funding |
| `n_project_links` | how many projects claim this outcome. Greater than one for 612 outcomes |
| `type_ambiguous` | true where the sources disagreed about the type. One record |
| `output_field`, `output_field_tier` | the outcome-side discipline, where the DOI resolved to one. 7,384 of 9,612 publications |
| `openalex_*`, `scopus_*`, `wos_*` | source-specific fields kept under their own prefixes rather than merged, so provenance is never lost |
| `impact`, `gtr_author` | GtR-specific fields |

### Text completeness, read this before any topic modelling

The build prints these every run so a regression is visible.

| | Rows | No title | No abstract | No DOI |
|---|---:|---:|---:|---:|
| all outcomes | 20,302 | 9,551 | 3,768 | 11,769 |
| **publications only** | 9,612 | **5** | **3,110** | 1,142 |

The 9,551 missing titles look alarming and are not. They are almost entirely
disseminations (6,074), collaborations (1,621), further fundings (1,188) and
policy influences (625) — outcome types GtR records without a title. **Filter
to `type = 'publication'` and titles are effectively complete**, which is what
topic modelling for RQ2 needs.

Abstracts are the real constraint: 32% of publications have none. Note also
that where an abstract came from a GtR outcome record rather than a
bibliographic source it is a *project description* written by the grant
holder, not a publication abstract. The two are different registers and
mixing them will distort any topic model. Check `doi_norm` is present as a
proxy for a genuine bibliographic record before using `abstract` as one.

## `project_outcomes` — 21,154 rows

The input-to-output join. One row per project-outcome pair.

| Column | Meaning |
|---|---|
| `project_id`, `global_outcome_id` | composite primary key |
| `gtr_outcome_id`, `openalex_outcome_id`, `wos_outcome_id`, `scopus_outcome_id` | the native identifier in each source that contributed |
| `source` | which sources reported this link, semicolon-separated |
| `match_basis` | how the sources were reconciled: `title`, `description` or `other` |

## `institutions` — 7,888 rows, and `project_institutions` — 2,462 rows

`institutions` is the registry, keyed on `institution_id` (`ror:...` for
resolved organisations, `local:...` otherwise) and carrying the canonical
name, organisation type, ROR metadata, the name variants that were unioned
into it, and `type_source` recording whether the type was assigned
automatically or by hand.

`project_institutions` is long format, so a project with three universities
and two companies is five rows. Carries `role` (lead or participant) and the
registry metadata joined on. **This is the table for network analysis and for
anything counting institutions rather than projects.**

---

## `source_outcome_links` — 30,460 rows

The pre-merge stacked links, one row per project-output-source. Kept so the
Methodology chapter's 616 figure remains reproducible from this database.
**Do not count rows in this table**: the same paper appears once per source
that reports it, and the WoS file is author-expanded, so it carries 663 more
rows than there are WoS papers. Count `COUNT(DISTINCT doi)` instead.

---

## `project_field_probabilities` — 1,640 rows, `publication_field_probabilities` — 6,436 rows

One row per project or per DOI, one column per discipline field, holding the
predicted probability. The Methodology chapter's finding is that single-label
assignment to interdisciplinary research is unreliable at the per-project
level, and that the analysis should be built from these distributions rather
than from hard labels (0.73 percentage points mean absolute error per field,
against 1.51 for hard assignment). **Prefer these tables to
`discipline_field` for any aggregate disciplinary claim.**

---

## `authors` — 41,637 rows, `outcome_authors` — 79,964 rows

`authors` is the disambiguated identity registry, keyed on `identity_id`, with
ORCID where known and the name variants unioned into each identity.
`outcome_authors` is long: one row per outcome-author position, carrying
`outcome_key`, `doi`, `author_position`, the raw and parsed name, `orcid`,
the native source identifier and `identity_id`.

## Reproducing the chapter's figures

```sql
SELECT COUNT(*)                                        AS n_projects,        -- 1640
       SUM(has_publication)                            AS with_publication,  -- 616
       SUM(1 - has_publication)                        AS without,           -- 1024
       ROUND(SUM(CASE WHEN funding_available = 1
                      THEN value_gbp END) / 1e6, 1)    AS funding_m_gbp      -- 752.0
FROM projects;
```

## A note on reading the database

SQLite needs file locking, which some synced and network folders do not
provide. If a query fails with `disk I/O error`, copy `ce_ecosystem.db` to a
local working directory first. On a normal local disk it opens fine.
